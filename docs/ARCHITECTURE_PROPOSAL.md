# PoB MCP 架构讨论稿

状态：**讨论中，部分方向已确定**。这份文档用于讨论模块怎么拆、接口怎么稳定，以及以后怎样安全地并行开发。它不代表这些能力已经全部实现。

已确定：采用**一个仓库、一个服务、内部模块化**；迁移时允许调整接口，优先整理成一致的新设计。工具层级、修改构筑时的失败处理和具体接口仍在讨论。

## 我们要解决什么

当前服务已经能调用 PoB 计算、查询国际服交易、读取行情并做有限的制作分析；但工具定义和路由仍集中在少数大文件中。不同功能同时修改这些文件时容易冲突；计算、价格和制作结论的来源与不确定性也需要有清晰的边界。

目标是让制作、交易、估价、计算等功能可以分别维护，并在集成后交叉验证。简体中文用于面向玩家的解释；代码、内部结果和协议保持英文或结构化格式。

## 第一项决定：部署和代码怎么拆

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A：单服务、内部模块化 | 保留一个 MCP 服务和一个仓库，代码按功能分模块，使用窄接口通信 | 本地安装简单，复用现有 PoB 和客户端配置；适合先完成可靠性工作 | 必须约束共享入口和依赖，防止重新长成大文件 |
| B：单仓库、多包 | 在同一仓库中将核心、交易、制作等拆为可独立构建的包 | 依赖边界更强，包可以独立测试和版本化 | 增加构建、发布、依赖和兼容管理；本地安装仍可保持单服务 |
| C：多个服务 | 计算、交易、制作各自运行，通过网络或进程通信 | 可以独立部署、扩缩容和故障隔离 | 本地启动、认证、版本兼容、监控和数据一致性明显更复杂 |

**已选 A，并参考 B 的边界设计。** 先把依赖方向和接口验证好；等某个模块确实需要独立发布或复用时，再讨论是否提成包。

## 建议的功能边界

```text
玩家 / AI 客户端
       │
MCP 入口：工具发现、参数和结果、能力开关
       │
       ├─ 构筑与计算：PoB 快照、技能、天赋、换装模拟
       ├─ 交易与估价：国际服交易查询、来源统计、行情和预算
       └─ 制作与物品数据：词缀、制作规则、有限范围的模拟
              │
      PoB / 官方交易 / poe.ninja 数据适配层
```

这只是职责边界，**不意味着现在就要拆成多个进程或多个 npm 包**。每个功能应能用替身数据做独立测试，只有真正需要 PoB、交易或行情时才通过适配接口调用。

### PoB 基础能力应放在底层

这里的“底层”是同一个服务内部共享的基础层，不是另起一个服务。建议按下面的依赖顺序组织：

```text
MCP 工具 / Skill / 组合流程
       ↓
天赋分析、装备比较、宝石比较、永恒珠宝搜索等功能
       ↓
PoB 基础能力：会话、版本、快照、构筑读写、计算和数据查询
       ↓
仓库自己的 PoB 适配层
       ↓
PoB 原版引擎和版本数据
```

基础层建议统一提供以下能力，具体接口名称尚未确定：

| 基础能力 | 给上层提供什么 | 上层使用示例 |
| --- | --- | --- |
| 引擎会话 | 启动、关闭、健康状态、版本和错误；同一会话中的请求串行 | 技能比较和天赋分析不各自管理 Lua 进程 |
| 构筑与快照 | 载入、读取、导出构筑，获取可用于隔离比较的快照 | 多个装备候选使用相同基准，不覆盖当前构筑 |
| 计算 | 在明确技能、配置和快照下读取角色、召唤物、伤害和防御指标 | 比较天赋或宝石时调用同一套 PoB 计算 |
| 基础数据 | 查询 PoB 版本对应的天赋、技能、装备、词缀和珠宝数据 | 词缀查询、珠宝搜索和装备分析复用同一数据版本 |
| 明确的修改操作 | 应用构筑、装备、技能或天赋变更，并返回实际执行状态 | 用户要求应用方案时，不由各模块直接修改 Lua 内部对象 |

PoB 原版引擎及其数据负责原版计算；仓库自己的适配层负责让服务调用它，并处理版本差异和本仓库已修复的兼容问题。优先调用 PoB 现成能力，不能为了某个上层模块再抄一套伤害公式或天赋树规则。PoB 没提供或无法核实的能力，应由上层明确标记，而不是伪装成原版结果。

例如：特殊升华名称和天赋树版本识别属于共享适配能力；永恒珠宝种子搜索可以是独立功能模块，使用底层提供的 PoB 树和珠宝数据。交易、行情、制作规则则有各自的数据源，不应塞进 PoB 底层，也不能因为引用了 PoB 数据就认为其交易或制作结论已被 PoB 验证。

当前这些能力已有实现，但集中在 `lua/pob_ops.lua`、`adapters/pob/bridge.ts` 和若干服务中；这里描述的是**整理后的目标边界**，不是声称已经完成抽离。PoB 更新后应记录引擎和数据版本，并重跑基础层对照测试；本仓库的适配代码和特色功能分别维护，避免同步原版时被覆盖。

### 基础层现状：可复用和仍需设计的部分

| 基础能力 | 当前能复用的实现 | 与目标边界的差距 |
| --- | --- | --- |
| 引擎生命周期 | `server/luaClientManager.ts` 管理 Lua 进程启动、关闭和重启；桥接能力查询返回适配器和操作列表 | 当前生命周期与具体桥接客户端耦合；进程重启后的原构筑恢复与调用方提示仍需纳入统一会话约定 |
| 版本 | 桥接 `version` 返回 PoB 声明的版本、分支、平台及适配器标识；构筑还包含天赋树版本 | 声明版本、实际引擎源码版本、游戏数据版本与构筑使用的树版本不是同一个概念；不能在取得不到时假设一致 |
| 构筑状态 | 已有载入、导出、角色信息、技能、装备、配置和天赋树读取 | 现有接口分别调用，不能天然证明多次读取来自同一时刻；需要清楚区分活动内存构筑与已保存文件 |
| 比较快照 | 装备比较已有 `item_comparison_snapshot`，返回构筑 XML 和一组基准数值，并有隔离引擎对照测试 | 当前不是通用的构筑版本标识，也不能只靠基准数值相等证明配置完全一致 |
| 计算与模拟 | `getStats`、`calcWith`、`compareItem` 已调用 PoB；宝石比较可以使用隔离引擎 | 调用方仍需分别处理指标名、缺失数据、模拟范围与错误；需要统一约定，同时保留不同计算的限制 |
| 数据和扩展 | 已有 PoB 天赋节点搜索、词缀权重查询，以及独立的永恒珠宝代码 | 底层 PoB 数据与上层搜索/排序要划清；版本差异和本仓库扩展仍需独立回归 |

这张表不要求一次性重写上述实现。建议先为**已有真实调用**建立稳定边界和对照测试，再逐步移动代码；每次迁移都确认计算输出和原构筑状态没有变化。如果上游 PoB 不提供某项版本或能力信息，结果要报告未知，而不是从仓库当前分支推断。

### PoB 底座接口草案

下面是职责草案，不是现有可调用的工具名：

| 能力 | 输入 | 输出与边界 |
| --- | --- | --- |
| 打开或读取会话 | 引擎位置、运行配置 | 会话状态、能力列表、能确认的版本；不因为引擎刚启动就声称已载入用户构筑 |
| 读取或捕获构筑 | 指定当前内存构筑或保存文件 | 构筑数据及来源；捕获快照必须在同一个一致的会话状态中完成 |
| 使用快照计算 | 快照、明确的技能和配置、需要的指标 | 分别返回角色、召唤物等指标及未知原因；隔离计算不修改原会话 |
| 执行明确变更 | 目标会话、变更内容、必要的基准状态 | 返回实际执行状态；冲突或错误时区分未执行、已执行和未知 |
| 查询版本数据 | 引擎和数据版本、查询条件 | 对应版本的数据、来源及未支持情况；不静默改用其他版本 |

**并发约定必须细化到会话，不只写“允许并发”。** 当前桥接客户端遇到同一进程的重叠请求会直接报错，并没有为所有调用自动排队；超时后会终止进程，防止迟到响应被当成下一次请求的结果。将来可考虑对单会话排队，或明确返回忙碌错误；隔离会话可以并行，但必须限制进程数、超时和资源，并分别跟踪结果。这些是待设计的接口行为，不是当前已经实现的调度器。

**构筑状态标识也不能直接沿用现有计数器。** 当前 `buildGeneration` 用于跟踪新建、载入和保存相关状态，不覆盖每一次装备、技能或配置修改。要用于“预览后检查构筑是否被改动”，需要另行设计覆盖范围，并用多种修改、引擎崩溃和快照往返验证。

还发现一个需要纳入后续基础层验收的现有风险：`new_build` 的桥接实现先创建新构筑，之后才检查部分职业和升华输入；错误返回不一定代表先前的内存状态没有变化。此处先记录为待验证和修复项，本轮架构讨论不改动运行逻辑。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| PoB 计算 | 读取构筑、管理快照、调用引擎、模拟与实际结果对照 | 决定交易报价或编造游戏规则 |
| 交易与估价 | 国际服赛季、官方筛选、挂牌样本、来源统计、行情与通货单位 | 把挂牌价当成交价，或从行情推导制作成功率 |
| 制作与物品数据 | 词缀数据、物品状态、已经核实的制作规则和有限模拟 | 未经验证就推断可制作性或概率 |
| MCP 入口 | 把工具和能力暴露给客户端、转发参数、保留兼容性 | 承担实际计算、规则和估价逻辑 |
| Skill | 指导 AI 选择工具、解释结果、提醒必要前提 | 复制一套价格或计算算法 |

永恒珠宝搜索建议作为计算域下的**独立功能模块**，按需依赖天赋树和 PoB 版本数据；不让交易、制作或普通伤害计算必须加载珠宝搜索。特殊升华名称则属于 PoB 数据和桥接层的兼容处理，应由计算核心统一提供给上层功能，而不是作为赛季专用功能散落在各个模块。两者都需要随 PoB 版本做真实数据回归。

## 现有功能盘点：迁移时影响哪里

下表描述现状及建议归属；**不是已经决定的新工具名称**。允许重新设计接口，但每项迁移必须核对调用方和结果差异。

| 已有工具或功能 | 当前用途 | 建议归属及迁移检查 |
| --- | --- | --- |
| `compare_equipment_candidate`、`compare_gem_setups`、`rank_support_gems` | 用 PoB 对照装备或技能方案 | 计算域；核对快照、角色与召唤物伤害、宝石是否生效及原构筑不变 |
| `get_passive_upgrades`、`suggest_masteries` | 试算天赋路径和专精 | 计算域；明确比较的伤害指标、路径点数和候选范围 |
| `find_timeless_jewel_seeds` | 搜索永恒珠宝种子 | 计算域独立功能；保留真实树版本和原版数据对照，不耦合一般技能分析 |
| `search_trade_items`、`estimate_comparable_item` | 国际服挂牌搜索和相似物品统计 | 交易域；保留 `securable`、来源覆盖、样本及通货，核对 `pob-economy` |
| `estimate_build_cost` | 基于 poe.ninja 的部分构筑参考价 | 估价域；保留未估价清单和获取时间，不能把参考小计当一口价总额 |
| `query_modifier_tiers`、`inspect_pob_item_affix_weight`、`classify_modifier_lines` | 查询词缀数据、PoB 权重和候选分类 | 物品数据与制作域；保留零权重、特殊规则和未知槽位的区别 |
| `compare_craft_budget`、`simulate_simple_annul` | 数学预算模型和一次剥离结果 | 制作域；保持外部概率来源与物品状态假设，核对 `pob-crafting` |

除两个制作工具的注册试点外，工具发现、路由与能力检查仍有旧代码；这说明架构切换尚未完成。后续要分别核对：工具是否被发现、能否直接调用、依赖关闭时是否拒绝调用、截断是否破坏原始数据，以及新旧客户端和 Skill 是否引用了变更后的名称。

## 已决定：已有功能的接口可以调整

- **接口设计优先**：允许改变工具名称、字段和调用方式，优先形成一致的新接口。
- **迁移仍需可核对**：为每项变更列出旧接口、新接口和受影响的 Skill、客户端及自动化；区分保留的兼容入口、明确移除的入口和暂未迁移的功能。是否设置过渡期按实际影响决定，不默认长期维护两套接口。

注册入口目前只试迁了两个不依赖外部服务的制作工具；其他工具还没有迁移。这个试点已经提交在本地，是否保留以及最终注册方式仍由架构讨论决定，接口允许按新设计调整。

## 还在讨论：工具层级和修改方式

一种可行设计是分两层：底层提供明确、可组合的基础能力，上层提供少量常见流程。例如：

- 基础能力：读取构筑快照、用指定物品做一次 PoB 预览、查询满足明确条件的一口价挂牌。
- 组合流程：针对一个装备槽，对指定搜索结果逐件做 PoB 对比，并同时返回价格与每件失败原因。

组合流程应调用同一套基础能力，而不是再实现一遍计算或交易规则；它要显示候选范围和限制，不能把“比较了几件”说成“全市场最优”。是否采用这一层级还在讨论。

涉及修改时，建议把**预览**和**应用**设计成不同操作：预览使用固定构筑快照，返回准备修改的内容和计算差异；应用明确指定要应用的方案，并检查所依据的构筑状态是否变化。调用方明确请求的应用可直接执行，不额外增加无必要的人工确认。多步修改只有在确实实现并验证回滚时才能称为原子操作；否则要说明部分完成状态。具体默认行为还在讨论。

## 待细化的技术接口

以下是讨论方向，不是已经生效的协议：

| 接口 | 建议传递的关键信息 | 需要证明的行为 |
| --- | --- | --- |
| PoB 快照 | 引擎版本、构筑状态标识、选中技能、配置、读取时间 | 同一快照上的多次对比使用相同基准；快照与原构筑不相互修改 |
| 计算结果 | 指标名、数值或未知状态、使用的快照、假设与诊断 | 角色和召唤物指标不混为一个数；模拟结果与实际修改对照 |
| 交易搜索 | 赛季、官方查询条件、`securable` 等状态、抓取时间、样本及通货 | 不丢筛选条件，不把缓存生成时间当成抓取时间 |
| 物品与制作 | 物品状态、游戏数据版本、规则来源、可证明的结果与未知项 | 无法确认的词缀、特殊机制或概率不转为确定结论 |
| 批量任务 | 每个子项的输入、完成/失败/未执行状态、实际结果 | 中途失败不会被误报为整批成功；不能假设一定回滚 |

不同领域保留各自字段，不强迫价格、构筑和制作使用同一套含糊的“大对象”。共用的只应是必要的信息约定，例如数据来源、时间、错误和未知状态。

### 工具注册与能力开关：现状和目标

当前试点把两个制作工具的说明和处理函数放在同一注册表；其余工具仍由旧代码分别决定“显示哪些工具”和“调用哪个处理函数”。PoB 未启用、交易未启用或某些认证条件未满足时，工具是否展示也由不同位置控制。试点注册表尚未统一管理这些条件，因此现在不能说架构已经完成。

建议新注册记录至少有：工具标识、输入和输出约定、处理函数、依赖的能力、对构筑的影响，以及结果是否允许截断。服务启动时检查标识冲突；工具列表和直接调用使用同一份能力判断。这里的“能力”指引擎或数据源是否可用，**不是用户权限控制**。如果数据源配置可用但实时请求失败，仍应返回明确错误，不应声称查询成功。

需要通过实际测试证明：

- PoB 和交易分别开启、关闭时，客户端看到的工具符合依赖关系；直接调用未开放的工具也不会绕过检查。
- 交易只读查询、需要登录的查询分别声明前提，不把认证信息写入工具结果或日志。
- 可截断的解释文本可以限制长度；PoB 导出码、XML 和结构化结果不能被截成无法解析的数据。
- 同一工具不会因注册重复、不同模块定义冲突或某个模块未加载而出现多个不一致版本。

### PoB 状态与多步修改：待讨论方案

现有 MCP 使用一个串行的 Lua 桥接进程；部分比较功能通过另一个隔离进程加载快照。桥接进程崩溃重启后，之前的内存构筑会丢失，不能把重新启动后的空构筑当成原构筑。这些是设计快照接口时必须保留的事实。

建议一个只读预览至少标识：使用的引擎及数据版本、构筑快照、技能/配置、输入候选、结果与未知项。若之后要应用预览方案，应检查当前构筑仍与预览基准一致；如果已变化，返回冲突并重新预览。该状态标识怎样生成、是否覆盖所有影响计算的数据，必须由序列化往返和真实 PoB 对照测试证明，**不能只比较几个伤害数值就认定构筑完全相同**。

对多步应用，要分别设计并测试：预检失败、某一步失败、回滚失败、引擎进程中断以及客户端中断后的状态。只有能证明全部状态恢复时才报告整体回滚；其余情况需要明确哪些步骤完成、哪些未执行、哪些状态未知。具体是否默认先预览，仍在等待讨论结果。

### 交易和制作的数据边界

交易模块保存用户选择的筛选条件、真实数据源和各次抓取时间。来自缓存的数据保留原始抓取时间，报告生成时间单独列出；不同通货不自动合成一个价格。来源统计应说明它覆盖的官方词缀来源、不可比较的条件和缺失数据，不能用零计数证明某来源不存在。

制作模块读取物品和词缀数据时，保留数据版本及具体物品状态。制作预算中的概率由有来源的规则或调用方输入提供；PoB 的词缀权重只能说明 PoB 在对应条件下的权重，不能单独算成成功率。游戏版本变更后，已验证规则要有可重跑的对照，而不是永久标记为正确。

## 跨模块必须约定的事

1. **计算输入和快照**：记录 PoB 版本、构筑、主技能和计算配置；模拟不能改变正在使用的构筑。一个 PoB 引擎的请求要串行，多个候选可以用隔离引擎并行。
2. **不确定性**：未读到、无法识别、超出支持范围分别标明，不把未知当成零；角色伤害和召唤物伤害分别报告，不能自动相加。
3. **国际服价格**：赛季必须明确；你的默认交易条件是可以去藏身处一口价购买的 `securable`。保留价格通货、样本、来源与真实抓取时间；poe.ninja 参考价不能冒充可购买挂牌。
4. **制作结论**：保存物品状态、游戏版本、规则来源和假设。PoB 权重不是制作成功率，无法核实的概率不猜。
5. **失败和部分完成**：只读模拟与修改构筑分开；批量修改如果没有原子回滚，必须说清哪些已完成、哪些未执行。

## 如何并发，又不让模块互相踩文件

架构确定后，每条开发线使用独立工作区和独立测试：

- 计算线：PoB 快照、技能、天赋、换装；用真实引擎对照模拟前后。
- 交易线：国际服查询、词缀来源统计、行情与造价；保留你已有的一口价规则。
- 制作线：词缀和可验证的制作规则、物品状态、受限模拟；概率必须有来源。

工具名称、共享协议、Lua 桥接、依赖锁文件与最终集成由一个负责人串行处理。每个模块先交付实现和本地验证，再进行整体联调；开发并发不等于对同一个可变 PoB 进程并发写入。

## 验收与发布

分别记录模块测试、真实 PoB 对照、MCP 端到端、国际服只读查询和本机客户端入口的结果；未运行或跳过的检查要明示。模块测试通过不代表真实引擎或实时交易已验证。

先在本地开发和集成，按你的要求暂不推送。架构和具体迁移顺序讨论确定后，再安排并行任务及统一发布。
